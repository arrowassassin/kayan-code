# Greedy, and when to trust it

Making change with US coins, you grab the biggest coin that fits — 25, then
10, then 1 — and it's always optimal. Making change with coins {1, 3, 4} for
6, the same instinct gives 4+1+1 (three coins) when 3+3 (two) wins. Same
strategy, one problem where it's provably right, one where it's provably
wrong. **Greedy is not a technique, it's a claim** — "the locally best choice
is safe" — and the claim needs a proof, or it's a guess.

That's the whole chapter: the two proof shapes that make greedy legitimate,
the classic failures, and the professional way to hedge when you're not sure.

## Proof shape 1: the exchange argument

The template, taught properly:

1. Suppose some optimal solution OPT disagrees with greedy's first choice —
   greedy picked g, OPT contains x instead.
2. Show you can **swap x for g inside OPT** without breaking feasibility or
   worsening the value.
3. Now there's an optimal solution agreeing with greedy on choice one. Repeat
   for every choice — an optimal solution agrees with greedy everywhere, so
   greedy is optimal.

Concrete run, [Non-overlapping Intervals](/problems/0435-non-overlapping-intervals)
(keep the most non-overlapping intervals; greedy = always keep the earliest
ending compatible one): OPT keeps A where greedy keeps B, and B ends no later
than A by greedy's rule. Swap A→B: B ends earlier, so everything OPT
scheduled after A still fits after B. Feasible, same count — the swap costs
nothing. QED, in four spoken sentences.

Why quarters work and {1,3,4} fails: with canonical coins, any use of small
coins summing past a big coin's value can be *exchanged* for the big coin
(two 10s + a 5 → a 25). With {1,3,4}, no such exchange exists — 4 doesn't
dominate combinations of 3s. When the exchange step won't go through,
**that's the signal to fall back to DP**
([Coin Change](/problems/0322-coin-change) is exactly this lesson).

## Proof shape 2: greedy stays ahead

Sometimes the cleaner argument is inductive: show that after k choices,
greedy's partial solution is **at least as good** as any other strategy's
partial solution — earliest end time so far, most tasks done so far, furthest
reach so far. If greedy never falls behind at any prefix, it can't lose at
the end.

Classic instance — Jump Game: track the furthest index reachable; greedy
"stays ahead" because no strategy can reach past the running maximum. One
sentence per step of the induction is enough in an interview; the phrase
"greedy stays ahead" itself signals you know the proof exists and what kind
it is.

## The canonical failures (know them cold)

| Problem | Tempting greedy | Why it fails | Right tool |
|---|---|---|---|
| [Coin Change](/problems/0322-coin-change), arbitrary coins | biggest coin first | no exchange: big coin ≠ dominated combos | DP |
| 0/1 knapsack | best value/weight ratio | can't take fractions; ratio choice blocks better sets | DP |
| [LIS](/problems/0300-longest-increasing-subsequence) | always extend with next bigger | early big element kills better futures | DP / patience |
| shortest path, negative edges | Dijkstra | settled ≠ final when edges refund cost | Bellman-Ford |

The shared failure mode: a local choice **forecloses combinations** you can't
see yet, and no swap repairs it.

## Heap-driven greedy: "most urgent first"

A recurring senior-level shape: repeatedly commit to the *currently* most
constrained resource, with a heap serving the argmax. The greedy claim is
"serve the scarcest thing first, it has the fewest future opportunities" —
an exchange argument in disguise.

[Reorganize String](/problems/0767-reorganize-string) — no two equal letters
adjacent. Always place the most frequent remaining letter (that isn't the one
just placed):

```python
def reorganize(s):
    heap = [(-c, ch) for ch, c in Counter(s).items()]
    heapq.heapify(heap)
    out, prev = [], None            # prev = letter benched for one turn
    while heap:
        c, ch = heapq.heappop(heap)
        out.append(ch)
        if prev: heapq.heappush(heap, prev)
        prev = (c + 1, ch) if c + 1 < 0 else None
    return ''.join(out) if len(out) == len(s) else ''
```

Why most-frequent-first: if the top letter's count ever exceeds half the
remaining slots, placement is impossible — spending its surplus *now* is the
only way to keep the future feasible. (Feasibility check up front:
`max_count <= (n + 1) // 2`.)

[Task Scheduler](/problems/0621-task-scheduler) is the same idea with a
cooldown of n instead of 1 — heap plus a cooldown queue, or the closed-form
`max(len(tasks), (max_count - 1) * (n + 1) + ties)`: the most frequent task
builds a frame of slots, everything else fills the gaps. Both formulations in
your pocket is the senior version.

Interval greedy, recapped from
[the intervals chapter](/study/02-patterns/23-sorting-intervals): sort by **end** for "keep the
most" ([0435](/problems/0435-non-overlapping-intervals)) — the exchange
argument above is the why. Sorting is greedy's usual first move: it arranges
the input so the local choice is well-defined.

## The professional hedge

In a live interview, the honest and *strong* move when greedy looks tempting:

> "My instinct is greedy — take the earliest ending interval. Let me check
> the exchange argument… yes, swapping any optimal choice for the greedy one
> can't hurt, because the greedy pick ends no later. If I couldn't complete
> that argument, I'd fall back to DP over the same choices."

This does three things: shows you know greedy needs justification, shows you
know the proof technique by name, and shows a safe failure path. DP is
always the fallback because greedy is DP with the claim "I only need the
best subproblem, not all of them" — if the claim dies, the DP is still there.
Never present greedy on vibes; a Google interviewer's next word will be
"why?", and "it seemed right" is the answer that sinks the round.

## Traps

- **Testing greedy on 3 examples and declaring victory** — the {1,3,4}
  counterexample passes many small tests. Argue, don't sample.
- **Right greedy, wrong sort** — earliest *start* instead of earliest *end*
  in interval selection; derive the axis from the exchange step.
- **Missing the feasibility precheck** in placement problems (Reorganize
  String's `(n+1)//2` bound) — greedy that runs into a wall late wastes the
  work.
- **Forgetting the heap's re-push** — benched items (cooldowns) must return.

## What the interviewer asks next

"Prove it" — exchange or stays-ahead, pick one and walk it. "What if the
coins/weights change to arbitrary values?" — recognize the exchange breaking
and pivot to DP without being pushed. "What's the complexity?" — usually
"sort dominates: O(n log n)" or "n heap operations: O(n log k)". "Can you
construct the actual schedule, not just the count?" — the heap version does;
know which formulation yields the artifact.
